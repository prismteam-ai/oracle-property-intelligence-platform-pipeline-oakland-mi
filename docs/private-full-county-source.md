# Complete protected county source attributes

Supplemental private manifest v4 requires exactly six roles: the existing owner, enrichment, permits and source-intake roles, plus county-parcels and county-addresses. Historical private manifest versions 1, 2 and 3 retain their exact earlier shapes. Canonical Property/Query contract 0.3.0 and public publication contents do not change. Novi Footprints is not an allowed v4 role: its explicit marketing restriction prevents promotion for the intended workflow.

The complete county acquisition retains 23 parcel and 13 address nongeometry attributes, including NAME1, NAME2, POSTALADDRESS, valuations, beds/baths, structure description and ZIP4. The two geometry-typed metadata fields are excluded by the explicit acquisition scope; numeric Shape.area and Shape.len remain source attributes. Source facts do not establish that a named or mailing party is a verified legal/beneficial owner, a contractor, or a continuous owner. REVISIONDATE is not a transfer date. No dedicated year-built or transfer field is present in the reviewed county schema.

Each county Parquet has exactly nine VARCHAR columns: version, source_id, native_id, public_snapshot_id, source_schema_sha256, source_record_json, record_digest, observed_at, and nullable property_id. The version is county-full-attributes-v1. Source IDs distinguish official-oakland-tax-parcel-full-attributes and official-oakland-site-address-full-attributes. The JSON preserves all source nongeometry attribute keys and scalar/null types. Unassigned records remain present with null property_id. The offline producer checks all JSON keys, types, stored-byte digests, native-ID uniqueness/fences, source counts and non-null property bindings before promoting an artifact.

Only the two new v4 file entries may carry the required metadata fields sourceSchemaSha256, sourceRecordCount, sourceValidationSha256 and sourceValidatedOffline=true. Those values and the file SHA are bound by the released private manifest digest. The validation SHA identifies the offline validation receipt; the runtime trusts this reviewed, hash-pinned producer attestation rather than parsing a million JSON objects again. Combined county rows are bounded at 1.2 million; each private file remains bounded at 128 MiB.

The runtime creates `private_county_parcels` and `private_county_addresses` as lazy `read_parquet` views over the verified local files. Boot verifies the outer schema and scans only narrow metadata columns for expected count/schema/source/snapshot/native-ID constraints, plus non-null canonical property FKs. It does not read or validate each source_record_json value in JavaScript at startup. Both complete file hashes enter the protected snapshot identity. Aggregate-only fullSourceAudits and coverage counts report retention and binding outcomes.

Lazy views require continued access to their exact verified files. The runtime configures an exact allowed_paths list for those files, disables general external access, and locks configuration. Tests verify that the lazy views still work while unlisted files and reenabling external access are denied. Cache directories/files use owner-only permissions and the existing three drained workers/atomic staging. `preparePrivateCache` derives the validated PRISM_PRIVATE_FULL_SOURCES configuration from the v4 manifest; direct configuration requires authenticated runtime mode.

All raw county JSON remains protected working data. No new Property DTO, agent/model tool, public endpoint or public-CAR projection includes the full fields. Private operator inspection can query these internal views; returned evidence contains only field names, counts, schemas, digests and validation outcomes. Names, addresses, contact/source values and full-source Parquet bytes stay outside Git and returned artifacts.

Existing-stack updates pre-stage every reviewed public/protected data object before CloudFormation can activate a new runtime prefix. The repository entrypoint now verifies fixed-stack S3 logical/output bindings, all local manifest/file hashes and sizes, actual all-public-access-block flags and expected bucket owner. Sequential SSE/SHA256 PutObject checks verify the returned server checksum; all data objects precede both manifests. Protected keys include the approved private-manifest hash. Failed checksums/bindings stop activation. A missing stack or missing required private bucket is a separate reviewed first-create/bootstrap operation and fails this update path; it never claims data was preactivated. The earlier private wrapper prestage is now redundant defense, not a hidden prerequisite for a repository update.
